Decision Block

DECISÃO

Multi-tenancy shared-db com tenant_id

Problema
Barbearias diferentes precisam de isolamento total de dados — um barbeiro de um salão não pode ver dados de outro.
Alternativas
Banco separado por tenant (alto custo); schema separado (complexidade de migrations); shared-db com tenant_id em cada tabela.
Escolha
Shared-db com tenant_id resolvido via middleware em cada request. Testes de isolamento retornam 404, não 403 — para não revelar que o recurso existe.
Resultado
Isolamento validado por testes. Zero vazamento de dados entre tenants em 8 meses de operação.
DECISÃO

PostgreSQL real no CI, não SQLite

Problema
Testes passando local (SQLite) mas falhando em produção (PostgreSQL) por diferenças de tipos e comportamento de constraints.
Escolha
Service container PostgreSQL efêmero no GitHub Actions — mesmo banco da produção, sobe e desce com o job.
Resultado
296 testes rodando contra PostgreSQL real a cada push. Nenhum bug só-em-produção após a mudança.

Incident Block (âmbar — máx 5 por tela)

● INCIDENTE

N+1 na listagem de vendas

Sintoma
Listagem de 20 vendas demorando visivelmente. Reclamação do cliente após semanas em produção.
Investigação
Django Debug Toolbar mostrou 61 queries para renderizar 20 registros: 1 geral + 20 para o barbeiro + 20 para o serviço + 20 para o pagamento.
Causa
Relações FK não carregadas previamente — ORM emitia uma query por objeto ao acessar cada FK no template.
Correção
select_related("barbeiro", "servico") + prefetch_related("pagamento") na queryset da view. 61 queries → 3 queries.
● INCIDENTE

networkidle nunca resolvia no EC2

Sintoma
Playwright aguardando networkidle e timeout esgotado em 100% das requests — mesmo para páginas que carregavam visualmente.
Causa
Scripts de analytics/telemetria do portal mantêm conexões de rede abertas indefinidamente. networkidle nunca é atingido.
Correção
Substituído por page.wait_for_selector() num elemento específico da página. Confiável e determinístico.
